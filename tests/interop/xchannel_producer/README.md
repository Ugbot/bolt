# Actual upstream xchannel test producer

This standalone Rust binary is a **test fixture**, outside Bolt's production
dependency and CMake graphs. It uses crates.io `xchannel = "=7.0.0"` and
`libc = "=0.2.183"`; xchannel itself brings its normal transitive dependencies.
No alternative framing writer or reader is embedded here. A C++ consumer must
run in a **separate process**, during or after this producer. Upstream forbids
concurrent writer/reader access to the same mapping in one process.

The inspected 7.0.0 crate's `.cargo_vcs_info.json` identifies upstream revision
`49063b06aa31cba3ddd659a19808f1aed2e6fc26`. Its `src/lib.rs` and `src/v4.rs`
match the researched revision. This tool writes upstream **format v4**, with
actual `WriterBuilder`, `try_reserve`, `commit` and `roll_file`; it does not
support format v3 or infer the client's deployed format.

Root compiled and ran this producer on macOS against the exact pinned crate,
then ran the separate native `verify_xchannel_fixture` consumer on four finite
fixtures: 1,200 records with 41 automatic Rolls; 300 records with 8 explicit
Rolls; 64 zero-length records; and an empty channel. Payload/metadata/identity
validation passed. Simultaneous live IPC and performance remain unqualified. Rust
1.88 or newer is required by upstream. Unix is the initial test platform;
geometry queries the actual OS page size via `libc::sysconf(_SC_PAGESIZE)` and
refuses a failed query. The pinned upstream crate is itself Unix-oriented, so
this is not a Windows build qualification.

## Fixture command

```text
bolt-xchannel-upstream-producer fixture BASE COUNT MAX_PAYLOAD REGION_SIZE FILE_ROLL_SIZE [EXPLICIT_ROLL_EVERY]
```

All numeric arguments are strict unsigned decimal. Bounds:

- `COUNT`: 0 through 10,000 user records, indexed from 0.
- `MAX_PAYLOAD`: 0 through 4,096 bytes. It is a length cap, not a fixed length;
  zero-length records are supported, including the all-zero-length case.
- `REGION_SIZE`: at least 4,096 bytes, at most 64 MiB, and an exact multiple of
  the actual OS page size. On a 16 KiB-page Mac, use 16,384 or a multiple.
- `FILE_ROLL_SIZE`: at least two regions and at most 64 MiB. Upstream rounds
  the initial file allocation up to a region multiple. The plan charges that
  rounded size for **every** retained segment, including an empty channel.
- `EXPLICIT_ROLL_EVERY`: default 0 disables explicit rolls; otherwise at most
  10,000. Roll immediately before record `i` when `i>0` and `i % interval==0`.
  There is no extra roll after the last record.

The maximum padded user record plus its 56-byte v4 Roll guard must fit a region
and a fresh segment. A 4,096-byte payload cap therefore cannot fit a 4,096-byte
region. Complete file/region placement and all explicit rolls are planned before
opening a writer; total retained logical file lengths must not exceed 64 MiB.
All files are retained: `keep_files` and background helpers are never enabled.
This cap is not a resident-RAM or physical-allocation guarantee.

`BASE` is the channel file's base path, not a directory. Its parent must already
exist. The file name is 1–128 ASCII letters/digits or `_.+-`; the resolved UTF-8
absolute path is at most 4,096 bytes. The producer canonicalizes the parent and
refuses if **any** existing sibling has the same name or starts with `name.`,
including symlinks, partials, stale segment files and unrelated dotted siblings.
Directory inspection refuses above 100,000 entries. The test runner must provide
an exclusively owned parent/prefix; this preflight is not a multi-writer lock.
No cleanup, unlink or retry is implemented. On failure, partial output may remain;
inspect it and use a new base. Never reuse an existing channel as a fresh fixture.
Upstream has recovery/partial-sweep behavior, so rejecting every prefixed sibling
before calling its builder is intentional.

Example for a fresh path supplied by the test owner:

```sh
cargo build --manifest-path extern/bolt/tests/interop/xchannel_producer/Cargo.toml --release
extern/bolt/tests/interop/xchannel_producer/target/release/bolt-xchannel-upstream-producer \
  fixture /private/tmp/OWNED-DIRECTORY/channel 300 1024 16384 65536 37
```

The producer creates no parent directory and deletes nothing. There is no Rust
consumer. A root-owned C++ optional external-fixture test must open this actual
output, check the incarnation and payloads, repeat peeks without cursor movement,
skip/consume and follow authentic region Skip / file Roll records. Record count
is supplied externally: an uncommitted tail is not a fabricated EOF record.

## Deterministic fixture protocol

Fixed channel name: `bolt-xchannel-v4-fixture`. Fixed nonzero generation:
`0x4732584348340001`. The starting absolute record index is 0. Physical v4 file
instance IDs are generated by upstream and deliberately are **not** hardcoded.
For record index `i` and payload offset `j`:

```text
length(i) = (73*i + 19) % (MAX_PAYLOAD + 1)
payload(i,j) = (17*i + 31*j + (j >> 3)) & 255
message_type(i) = 0x4000 + (i % 17)
user_meta_u64(i) = i
```

These are opaque fixture bytes, not SBE, Source23 or market events. No timestamp
or latency claim attaches to fixture metadata. Suggested consumer schedule:
peek each user record twice, compare header/payload and unchanged cursor, then
skip if `i % 7 == 3`, otherwise consume. Validate even skipped payloads through
the peeks. `MAX_PAYLOAD=0` and selected larger runs can exercise empty records;
small geometry/longer runs exercise authentic upstream region skips and rolls.
Choose enough records for the desired branch; the tool reports its predicted
region skip count and exact per-record file ordinals, rather than claiming every
valid invocation includes every boundary.

The manifest checksum starts at FNV-1a64 offset `0xcbf29ce484222325`. For every
record, fold its index as 8 little-endian bytes, length as 4 little-endian bytes,
message type as 2 little-endian bytes, then every payload byte. Each byte step is
`h = ((h XOR byte) * 0x100000001b3) mod 2^64`. It includes all records, including
those the external consumer skips. Empty input's checksum is the initial offset.

The placement model follows the inspected `src/lib.rs` exactly: first header at
file offset 208, 16-byte envelope, 8-byte aligned records, and 56 bytes reserved
for a possible Roll after each reservation. File-size admission is tested before
region crossing; a region crossing emits upstream's Skip and starts its next
header at the next region boundary. Explicit rolls reset the next header to 208.
The producer checks the real writer's `file_sequence()` against the model for
each reservation and `next_record_index()` after every commit.

Upstream's inspected `make_channel_file_path` uses **`BASE` for sequence 0** and
**`BASE.N` for sequence N>0**, appending to the original file name (so `a.log`
becomes `a.log.1`). It does not use `BASE.0`, numeric padding or an extension
replacement. Published segments remain contiguous because this harness enables
no pruning. Partial creation names belong to upstream and must not be opened as
published history.

Success writes exactly one JSON object and newline to stdout; no progress output.
Failure writes a diagnostic to stderr and exits 2; success exits 0. Require exit
0 and a complete parsed manifest before accepting stdout. The manifest v1 keys
are:

```text
manifest_version, mode, xchannel_version, format_version, generation, base,
channel_name, count, max_payload, region_size, file_roll_size,
explicit_roll_every, payload_algorithm, length_algorithm,
message_type_algorithm, user_meta, clock, checksum_algorithm, checksum_hex,
consumer_schedule, region_skip_count, retained_bytes, file_ordinal_expectation
```

`base` is resolved absolute UTF-8. `checksum_hex` is exactly 16 lowercase hex
digits. `clock` is JSON null; `user_meta` is `record_index`.
`file_ordinal_expectation` has `first=0`, `last`, `count=last+1`, and
`record_file_ordinals` containing exactly COUNT sequence numbers. Other algorithm
strings and the consumer schedule are fixed literals in `main.rs`. Geometry and
capacity refusals occur before file creation; IO/upstream errors after creation
leave their observable prefix and never trigger an automatic retry or deletion.

## Reserved replay benchmark contract (not implemented)

Only `fixture` is implemented. A later `replay-v1` mode will use a bounded binary
frame-input file loaded entirely before opening the channel; it will not generate
or reinterpret market rows in the publication loop. Intended command:

```text
replay-v1 BASE FRAME_FILE UPDATES_PER_SECOND REPEAT_COUNT REGION_SIZE FILE_ROLL_SIZE
```

The input format is little-endian: 8-byte magic `BXRP0001`, UInt32 frame count,
UInt32 reserved0, followed by frame_count entries of UInt32 payload_length,
UInt16 message_type, UInt16 flags, and exactly payload_length opaque bytes.
Only flag bit0 (`update_end`) is admitted; the last frame must have it set and
every complete update must contain at least one frame. No trailing bytes.
Bounds: at most 10,000 frames, 4,096 bytes/frame and 64 MiB total file; at most
10,000,000 complete updates/s, repeat count 1..10,000 and checked total committed
frames <=10,000,000. Reject unknown flags, incomplete final updates, overflow and
oversized input before channel creation. The retained-file 64 MiB cap still
applies to the **whole** repeated run; no implicit pruning.

Rate is complete updates/s, not messages/s. Frames inside one complete update
are contiguous; pace update starts from an absolute scheduled epoch plus update
ordinal/rate. Record intended schedule separately from actual observations so
lateness/queueing are visible; do not relabel a closed-loop rate as open-loop.
Immediately **before each `try_reserve`**, sample the Unix OS
`libc::clock_gettime(libc::CLOCK_MONOTONIC, ...)` and pass its checked UInt64
nanoseconds unchanged to `commit(..., user_meta_u64)`. The C++ consumer must name
and sample that same OS clock immediately after successful record observation.
Reject failed/negative/overflowing clock readings; other clocks/platforms are
explicitly unsupported initially. A stamp made after commit cannot describe
publication latency and is forbidden by this contract. Warmup, CPU placement,
duration, loss, offered/accepted/completed rates and percentile aggregation remain
benchmark-owner work; this reservation implements no speculative benchmark loop.

The tool establishes no fsync/power-loss durability, allocation plateau, native
DataFrame computation, paper action completion or HFT/tail-latency result.
