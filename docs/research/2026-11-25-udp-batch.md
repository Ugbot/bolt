# Batched datagram I/O and reactor readiness (G2CHK-1271)

Plan item 3 of Gestalt2 `docs/research/2026-11-24-reactor-vs-venus-libuv-seastar.md`. This is the
datagram layer that the shared `bolt::net` transport (VSR plan slice B0) builds on. The B0 agent
reviewed it and asked for: a lend/release flag, writable receive buffers, a GRO iterator, bytes only,
readiness in bolt, socket setters, and drop counters. All are below.

## What landed

`bolt/net/bolt_udp_batch.h`, plus `bolt_udp_limits.h`:

- **`udp_recv_batch(ep, batch, max)`.**
  - Linux: `recvmmsg` with `UDP_GRO`. `msg_controllen` is reset on every call.
  - Darwin: `recvmsg_x`. Each datagram gets one spill byte, because `recvmsg_x` does not report
    MSG_TRUNC per entry.
  - Elsewhere: a `recvfrom` loop.
  - Never blocks: an empty socket returns 0.
- **`udp_send_batch(ep, batch, first, n, gso)`.**
  - Linux: `sendmmsg`. Same-peer, same-size runs go out as one `UDP_SEGMENT` message. A short final
    segment ends a run. A run holds at most 64 segments and 65,000 bytes.
  - On EIO, GSO is switched off in the stats and the run is sent as single datagrams.
  - A short count is resumed once.
  - Darwin uses `sendmsg_x`; elsewhere a `sendto` loop.
- **Slots** are caller-owned `{buf, cap, len, peer, segment, flags}`. A send takes any pointer, so a
  retain ring's sealed fragment goes out with no copy. Receive buffers are writable.
  - `kUdpSlotHeld` lends a slot to the protocol; receive skips it until the flag is cleared.
  - `kUdpSlotTruncated` marks an oversize datagram.
  - `udp_slot_datagrams(slot)` iterates the datagrams of a GRO slot.
- **Socket setters:**
  - `udp_endpoint_enable_gro`;
  - `udp_endpoint_enable_drop_count`: SO_RXQ_OVFL, reported as `UdpBatchStats::kernel_drops`;
  - `udp_endpoint_set_send_buffer`;
  - `udp_multicast_set_loop`.

  The existing ones are recv buffer, publisher TTL/IF, join/leave/join_source and reuse.
- **Reactor.** `async_io::readable_async(fd)` and `IODispatcher::async_readable(fd)` wait for
  readiness without doing any I/O, for protocols that read with their own calls (batch receive, TLS,
  framing). Call it after a non-blocking read returned would-block.
  - kqueue/epoll: the register-once read slot.
  - io_uring: a one-shot `POLL_ADD`.
  - IOCP: not available (returns -1).
- **chukonu.** `src/transport/udp_endpoint.cpp` is deleted (chukonu branch
  `udp/g2chk1271-drop-dead-udp-endpoint`). It was a dead, 128-line-drifted copy; CMake already built
  `bolt::net`'s. BatchSender/Receiver moving onto the batch calls is part of B0's reliable-UDP work.

## Tests (test_bolt_udp_batch)

- an empty socket returns 0;
- one call takes 40 queued datagrams, in order, with sizes and sources;
- an oversize datagram is flagged truncated (the Darwin spill byte);
- held slots are skipped;
- a 32-slot send batch arrives in full and goes out as GSO on Linux;
- GRO coalesces on Linux, and the slot iterator splits 10 × 500 B;
- multicast loopback;
- a reactor receive loop on `async_readable` takes 5,000 datagrams with fewer readiness waits than
  datagrams.

The suite passes on macOS and in the Linux container (8 tests, GSO and GRO included).

## Measurements

UDP sink receive, one receiver thread, the same bench set (`udp_servers boltbatch`: batch receive,
then `async_readable`). Datagrams/s, medians:

| | bolt main (per datagram) | G2CHK-1269 per datagram | **batch** | libuv | raw loop |
|---|---|---|---|---|---|
| macOS (kqueue, `recvmsg_x`) | 263k | 383k | **654k** | 466k | 468k |
| Linux VM (epoll / io_uring) | 662k / 1.96M | 1.69M / 2.02M | 1.70M / 1.93M | 1.64M | 1.89M |

- **macOS.** Batch receive is 2.5× bolt main and 1.4× libuv.
- **Linux VM.** Every receiver except main epoll runs at the two senders' rate, so the VM cannot rank
  them. It needs a host with more free cores (the quiet-host rerun, G2CHK-1277).
- **UDP ping-pong p50.** Batch and per-datagram are the same: macOS 22.5 µs, Linux 18.7 µs. Linux main
  is 29.6 µs.
